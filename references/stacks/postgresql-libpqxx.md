# PostgreSQL 与 libpqxx 规范

适用范围：PostgreSQL 服务端迁移 + C++ 数据访问层（CMake `libpqxx::pqxx`；若使用 Drogon 异步 `DbClient` 见 [Drogon 指南](drogon.md)）。

## 1. `libpqxx` 连接生命周期与参数化查询

- **核对主版本 API**：`libpqxx` 6.x / 7.x 在参数化接口（`exec_params` vs `exec(zview, params)`）、异常类型与连接串选项上存在差异；接入前核对所安装版本的官方头文件，不直接套用跨大版本片段。
- **连接池租约纪律**：一个数据库连接与当前 `pqxx::work` 事务只能由单个执行上下文独占。从连接池借出的连接，必须在 `transaction` 与 `result` 对象彻底析构后才能归还池中；获取租约设置明确等待超时，防止上游突发流量雪崩。
- **参数绑定与动态标识符**：所有值走参数绑定；遇到无法参数化的动态表名、列名或排序方向（`ASC`/`DESC`），必须通过**代码级固定白名单**映射，再用 `conn.quote_name(...)` 转义，绝不直接拼接用户输入。

## 2. 并发事务、错误语义与未知提交状态

| SQLSTATE / 故障情形 | 正确处理策略 |
| --- | --- |
| 唯一约束 / 外键冲突 (`23505` / `23503`) | 不可重试；中止失败事务，映射为业务冲突/校验失败错误（如 HTTP 409/400）。 |
| 序列化失败 / 死锁 (`40001` / `40P01`) | 允许在总时间预算与最大重试次数内**重跑完整业务事务**（必须保证事务外无不可逆副作用）。 |
| 调用 `commit()` 时连接突然断开 | **禁止假定已回滚并盲目重放写操作！** 事务可能已在服务端提交但回包丢失；向调用方返回待确认或先按唯一业务 ID 查库核对真实状态。 |

## 3. PostgreSQL 迁移与锁安全

- **区分可事务与非事务 DDL**：`CREATE INDEX CONCURRENTLY`、`ALTER TYPE ... ADD VALUE`（部分老版本限制）不能运行在普通事务块内；执行失败后需主动清理残余 `INVALID` 索引。
- **滚动发布四步法（Expand → Backfill → Switch → Contract）**：先加可空列或新表并发布兼容代码 → 分批小事务回填历史行 → 切换读写 → 确认旧版本下线后再收缩删除旧列/加 `NOT NULL`。避免在大表上直接执行长时间 `ACCESS EXCLUSIVE` 锁表的变更与回填。
- **跨系统一致性**：数据库事务不能回滚事务外发出的 RPC 或消息；同时落库与发通知时采用 Transactional Outbox 模式或明确幂等补偿机制。

## 4. 验证要点

- 必须使用真实目标版本的 PostgreSQL 实例测试（**严禁拿 SQLite 代替 PostgreSQL 语法、锁与序列化并发语义**）：
  - 并发连接池租约耗尽与超时测试。
  - 从代表性旧 schema 迁移并验证非空历史行处理、前/后两代应用代码兼容读写、事务回滚无残留写入及断连后按业务 ID 幂等核对。
